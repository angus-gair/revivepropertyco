## Real-Time Update Interaction Design

### Scenario: New hipages lead arrives via LISTEN/NOTIFY

**Visual feedback sequence:**

1. **PostgreSQL NOTIFY fires** (backend receives `hipages_leads_updated` event)
2. **Backend broadcasts via WebSocket** (or polling fallback every 30s)
3. **Admin dashboard receives event** → Show toast notification:
   ```
   Toast slides in from top-right (orange background)
   Icon: bell or alert-circle
   Text: "3 new leads from hipages"
   Auto-dismiss: 5 seconds
   Click: Navigate to hipages tab
   ```
4. **Badge appears on "hipages Leads" tab**:
   ```
   Orange circle with white number: "3"
   Positioned: top-right of tab label
   Animation: bounce/scale on appearance
   Dismiss: Click tab (badge disappears, data refreshes)
   ```
5. **Table auto-refreshes** (if already on hipages tab):
   ```
   New rows slide in from top (framer-motion layout animation)
   New rows highlighted with subtle orange glow (fades after 2s)
   Scroll to top if needed
   ```

**Fallback (if WebSockets unavailable):**
- Poll backend every 30 seconds
- Check `scraped_at` timestamp for new leads
- Same visual feedback, just delayed

**Rationale:** Real-time updates are a key requirement (RESEARCH.md section "Real-Time Sync Strategy"). PostgreSQL LISTEN/NOTIFY provides push notifications, but UI must handle them gracefully.

## Lead Accept/Reject Workflow

### Accept Lead Flow

**Trigger:** Click "Accept Lead" button in hipages lead modal

**Interaction sequence:**
1. **Primary dialog appears** (modal overlay):
   ```
   Title: "Convert hipages Lead to CRM"
   Body: "This will create a new CRM lead from hipages data. The hipages lead will be marked as synced."
   Lead preview: Name, suburb, job type, credits
   Buttons: "Convert to CRM Lead" (primary, orange), "Cancel" (secondary)

   Loading state (during API call):
   - Button shows spinner
   - Button text: "Converting..."
   - Modal backdrop prevents clicks
   ```
2. **Success state** (API returns 200):
   ```
   Toast: "Lead converted successfully"
   Modal closes
   Row updates: Status changes to "Synced to CRM"
   Row action button: Changes to "View in CRM" (link to /admin/leads/{id})
   Tab badge: Decrements count
   ```
3. **Error state** (API returns 500/404):
   ```
   Toast: "Failed to convert lead. Please try again."
   Modal remains open
   Button resets to "Convert to CRM Lead"
   ```

### Reject Lead Flow

**Trigger:** Click "Reject Lead" button (secondary, red)

**Interaction sequence:**
1. **Confirmation dialog appears**:
   ```
   Title: "Reject Lead"
   Body: "This will mark the lead as rejected and remove it from your active leads."
   Warning text: "This action cannot be undone."
   Buttons: "Reject Lead" (red, destructive), "Cancel" (secondary)
   ```
2. **Confirmation** → API call to `/api/hipages/leads/:id/reject`
3. **Success** → Row removed from table (fade-out animation), toast: "Lead rejected"

**Rationale:** Accept/reject is the core workflow for hipages leads (RESEARCH.md section "Data Model Mapping"). Clear confirmation prevents accidental rejections.

### Real-Time Sync Backend

**WebSocket endpoint:** `ws://localhost:8080` (existing backend infrastructure)
**Event name:** `hipages:leadsUpdated` (from RESEARCH.md Example 3)
**Payload:** `{ count: number, leads: HipagesLead[] }`

**Frontend integration:**
```typescript
// In HipagesLeadsPage.tsx
useEffect(() => {
  const ws = new WebSocket('ws://localhost:8080');
  ws.onmessage = (event) => {
    const data = JSON.parse(event.data);
    if (data.type === 'hipages:leadsUpdated') {
      setNewLeadsCount(data.payload.count);
      // Show toast, update badge
    }
  };
  return () => ws.close();
}, []);
```
